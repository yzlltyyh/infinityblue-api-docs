# Rerank

Reranking is a second-pass relevance model that reorders a short list of candidate documents based on a query. It typically sits between a fast vector recall step and the final prompt sent to a chat model. The interactive reference below is generated from `openapi/openapi.yaml`.

## Endpoint

<Card title="POST /v1/rerank" icon="arrow-up-arrow-down" href="/api-reference/rerank/create">
    Score a list of documents against a query. Returns the documents sorted by relevance, each with a `relevance_score`.
</Card>

## Why rerank

A vector store can recall 100 candidates in a few milliseconds, but its top-10 is not always the best top-10. Rerank models apply a more expensive cross-encoder that reads the query and each document together, so they catch nuance that pure vector similarity misses.

<CardGroup cols={2}>
  <Card title="Higher precision" icon="crosshairs">
    Improves the precision of the top results, especially for long, technical, or ambiguous queries.
  </Card>
  <Card title="Cheaper than re-embedding" icon="piggy-bank">
    Rerank models are tuned for small lists, so the cost is much lower than re-embedding the entire corpus at query time.
  </Card>
  <Card title="Plays well with RAG" icon="link">
    Combine with [Embeddings](/api-reference/embeddings) for a hybrid pipeline that beats either component alone.
  </Card>
  <Card title="Drop-in" icon="plug">
    Accepts a list of strings, documents, or pre-existing IDs. No retraining required.
  </Card>
</CardGroup>

## Minimal example

```bash
curl https://api.infinityblue.com/v1/rerank \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "rerank-3",
    "query": "How do I rotate my API key?",
    "documents": [
      "To rotate a key, visit Settings → API Keys and click Rotate.",
      "Recipes for sourdough bread require a long fermentation.",
      "Billing questions are answered in the pricing FAQ."
    ],
    "top_n": 3
  }'
```

The response:

```json
{
  "model": "rerank-3",
  "results": [
    {"index": 0, "relevance_score": 0.92, "document": "To rotate a key..."},
    {"index": 2, "relevance_score": 0.18, "document": "Billing questions..."},
    {"index": 1, "relevance_score": 0.04, "document": "Recipes for sourdough..."}
  ]
}
```

## Hybrid pipeline

A typical RAG flow looks like this:

<Steps>
  <Step title="Recall">
    Embed the query and pull the top 50 candidates from your vector store. Optionally fuse with BM25 keyword search for a hybrid recall.
  </Step>
  <Step title="Rerank">
    Send the 50 candidates and the original query to the rerank endpoint. Ask for `top_n` between 5 and 20.
  </Step>
  <Step title="Prompt">
    Feed the top reranked documents to a chat model along with the user question. Use the model's response as the answer.
  </Step>
  <Step title="Evaluate">
    Track offline metrics such as nDCG@10 and MRR on a labeled eval set. Adjust `top_n` and the recall depth to optimize latency and quality.
  </Step>
</Steps>

<Tip>
  Most production systems see the largest quality lift when reranking the top 30-100 candidates. Reranking more than that slows the pipeline without meaningfully changing the final ordering.
</Tip>

## Limits and gotchas

- Rerank scores are useful for ordering, not for absolute thresholds. Do not compare scores across requests.
- The endpoint charges per document, not per request. Trim your candidate list before calling.
- If you pass a pre-existing document ID instead of text, include the ID in the `metadata` field so downstream code can resolve the full document.
